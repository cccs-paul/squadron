# Phase 9: Credential Delegation & End-to-End Agent Git Workflow

**Created:** 2026-04-05
**Status:** Planned (not yet implemented)

## Overview

Wire up delegated credential resolution across all modules so agents can clone repos, create branches, commit, push, and create PRs on behalf of users — without requiring the user's private key. Implement four credential strategies (PAT, OAuth2, Deploy Keys, GitHub App installation tokens), dual-mode review agent (internal AI review + optional bot reviewer on the git provider), and the complete workspace-to-PR lifecycle.

## Architecture

### Credential Resolution Chain

When an agent needs to perform git or platform API operations on behalf of a user, the system tries credential strategies in priority order:

```
1. User's OAuth2 token → auto-refresh if expired
2. User's PAT
3. Deploy Key / SSH Key → for git ops only; PAT/OAuth2 for API calls
4. GitHub App installation token → GitHub connections only
5. Fail → clear error prompting user to link credentials
```

### End-to-End Agent Flow

```
Orchestrator (state transition)
  │
  ▼ NATS event (TaskStateChangedEvent + enriched TaskContext)
  │
TaskStateDispatcher (squadron-agent)
  │
  ├─ PROPOSE_CODE ─▶ WorkspaceLifecycleService
  │                   │
  │                   ├─ CredentialClient.resolveCredentials(userId, connectionId, GIT_CLONE)
  │                   ├─ WorkspaceService.createWorkspace() (with token/sshKey)
  │                   ├─ auto-clones repo inside container
  │                   ├─ GitClient.generateBranchName()
  │                   └─ git checkout -b {branch} inside container
  │                   │
  │                   ▼
  │                 CodingAgentService (LLM tool loop in workspace)
  │                   │
  │                   ▼
  │                 CodeGenerationService
  │                   ├─ git add -A && git commit
  │                   ├─ CredentialClient.resolveCredentials(userId, connectionId, GIT_PUSH)
  │                   ├─ git push origin {branch} (with token/sshKey)
  │                   ├─ GitClient.createPullRequest() (with resolved token)
  │                   └─ Auto-assign review bot if enabled
  │
  ├─ REVIEW ────▶ ReviewAgentService
  │                 ├─ Find existing workspace (or create for external PR)
  │                 ├─ git diff main...HEAD
  │                 ├─ LLM review loop (max 10 iterations)
  │                 ├─ Parse findings → APPROVED / CHANGES_REQUESTED
  │                 ├─ Submit internal review record
  │                 └─ If ReviewBotConfig enabled:
  │                     ├─ Post comments on git provider as bot
  │                     └─ Set review status (approve/reject) as bot
  │
  ├─ QA ────────▶ QAAgentService (reuse workspace)
  │
  └─ MERGE ─────▶ MergeService
                    ├─ Check review gate
                    ├─ Check mergeability
                    ├─ Merge PR via platform adapter
                    └─ Destroy workspace (cleanup)
```

### Isolation Model

Each agent/task gets its **own workspace container** (K8s pod or Docker container):
- Own filesystem and git working directory at `/workspace`
- Own branch (generated by `BranchStrategyService` with template `{prefix}{taskId}/{slug}`)
- Own credential injection (token lives only in the container's git remote URL, cleaned up after operations)
- No stepping on toes — multiple agents on the same repo work on different branches in different containers

### Epic 1: Credential Resolution Service (squadron-platform + squadron-common)

The credential resolution layer that all other modules call to get a usable access token for a given user+connection.

#### 1.1 — Create `CredentialResolutionService` in squadron-platform

**Package:** `com.squadron.platform.service`
**File:** `squadron-platform/src/main/java/com/squadron/platform/service/CredentialResolutionService.java`

Single entry point that tries credential strategies in order:
1. User's OAuth2 token (from `user_platform_tokens` where `tokenType=oauth2`) → auto-refresh via existing `UserTokenService.getDecryptedAccessToken()`
2. User's PAT (from `user_platform_tokens` where `tokenType=pat`)

Dependencies: `UserTokenService`, `SshKeyService`, `GitHubAppTokenService`, `PlatformConnectionRepository`

**File:** Update `UserTokenService` in squadron-platform

When a user links a PAT via `POST /api/platforms/tokens/pat/link`, validate the token has sufficient permissions:

Return validation result: `{ valid: true, scopes: [...], missingScopes: [...] }`

### Epic 2: GitHub App Installation Token Strategy (squadron-platform)

#### 2.1 — Create `GitHubAppTokenService`

**Package:** `com.squadron.platform.service`
**File:** `squadron-platform/src/main/java/com/squadron/platform/service/GitHubAppTokenService.java`

Steps:
1. Load `app_id`, `private_key_pem` (encrypted in `PlatformConnection.credentials`), `installation_id` from connection
2. Generate JWT signed with app's private key (RS256, 10-min expiry, `iss=app_id`) using Nimbus JOSE
3. Exchange JWT for installation access token via `POST https://api.github.com/app/installations/{installation_id}/access_tokens`
4. Optionally scope to specific repositories via `repositories` or `repository_ids` request body
5. Cache tokens in-memory with TTL = `min(expires_at - now - 60s, 55 min)` to avoid unnecessary regeneration

**Tests:** JWT generation, token exchange (mocked WebClient), caching, expiry handling. ~10 tests.

### Epic 6: Workspace Lifecycle Integration (squadron-agent + squadron-workspace)

#### 6.1 — Create `WorkspaceLifecycleService`

**Package:** `com.squadron.agent.service`
**File:** `squadron-agent/src/main/java/com/squadron/agent/service/WorkspaceLifecycleService.java`

```java
public WorkspaceInfo provisionWorkspace(TaskContext taskContext) {
    // 1. Resolve credentials
    var creds = credentialClient.resolveCredentials(
        taskContext.getUserId(), taskContext.getConnectionId(), CredentialPurpose.GIT_CLONE);

    // 2. Create workspace
    var workspace = workspaceClient.createWorkspace(CreateWorkspaceRequest.builder()
        .tenantId(taskContext.getTenantId())
        .taskId(taskContext.getTaskId())
        .userId(taskContext.getUserId())
        .repoUrl(taskContext.getRepoUrl())
        .branch(taskContext.getDefaultBranch())
        .accessToken(creds.getGitAuthMode() == HTTPS_TOKEN ? creds.getAccessToken() : null)
        .sshPrivateKey(creds.getGitAuthMode() == SSH_KEY ? creds.getSshPrivateKey() : null)
        .build());

    // 3. Generate and create branch
    String branchName = gitClient.generateBranchName(
        taskContext.getTenantId(), taskContext.getProjectId(),
        taskContext.getTaskId(), taskContext.getTitle());

    workspaceClient.createBranch(workspace.getId(), branchName, taskContext.getDefaultBranch());

    return WorkspaceInfo.builder()
        .workspaceId(workspace.getId())
        .branchName(branchName)
        .repoUrl(taskContext.getRepoUrl())
        .gitAuthMode(creds.getGitAuthMode())
        .build();
}
```

```
Epic 1 (Credential Resolution) ─┬─▶ Epic 2 (GitHub App)
                                 ├─▶ Epic 3 (Deploy Keys)
                                 └─▶ Epic 4 (Feign Clients) ─┬─▶ Epic 6 (Workspace Lifecycle)
                                                              ├─▶ Epic 7 (PR Delegation)
                                                              └─▶ Epic 8 (Review Bot)
Epic 5 (Task Context) ───────────────▶ Epic 6 (Workspace Lifecycle)
Epic 9 (Security) ── independent, do alongside Epics 6-8
Epic 10 (Frontend) ── depends on Epics 2, 3, 8 (backend APIs must exist)
Epic 11 (Integration) ── depends on all other epics
```

1. Epic 1 (foundation) + Epic 1.2/1.3 (common DTOs)
2. Epic 2 + Epic 3 (credential strategies)
3. Epic 4 (Feign clients)
4. Epic 5 (task context enrichment)
5. Epic 6 (workspace lifecycle) + Epic 7 (PR delegation)
